## 方案选择

1. **推荐：完整 ingest 规划 + 确定性应用。** 保留当前审核体验和受保护写入器，把 ingest 步骤作为受编排的后台阶段。流程及内容均可审阅。
2. 直接让 `/wiki-ingest` 修改临时 Wiki，再计算 diff：隔离成本更高，需要拦截脚本、锁、manifest 和其他输出；适合未来已有成熟沙箱执行器时考虑。
3. 批准后直接运行能写正式 Wiki 的 agent：无法保证写入等于审核内容，不符合本功能的既定要求。

采用第一种。流程规范来自现有 Wiki 和 ingest 技能，文件修改仍由 ai-todos 执行。单纯在提示词增加“遵循 ingest”不能保证各步骤完成。

## 用户流程

```text
提取会话经验 → 逐项确认与意见 → 生成 ingest 方案
  → 处理重复和冲突 → 审阅完整变更与检查结果
  → 批准并写入 Wiki → 查看写入清单及持久化记录
```

“生成 ingest 方案”继续使用后台任务；各阶段显示读取、检索、融合、关联和校验进度。关闭弹窗不停止任务。断点绑定会话快照、审核版本、规范版本和依赖页面摘要，变化后不得复用旧方案。

审核页按功能折叠：

- 来源材料：归档范围、原文证据、会话定位、快照摘要。
- 已确认经验：结论、人工修正和未验证事项。
- 重复与冲突：相同知识、补充信息、适用范围差异、直接矛盾。
- 知识融合：每条经验对应哪些页面，为什么新建或合并。
- 配套更新：来源记录、人读版、双链、索引、hot 和日志。
- 写入预览：按文件展示 Markdown 与完整 diff，显示校验结果。

每个 ingest 步骤必须标为“已生成”“无需变更（说明原因）”或“阻塞”。完整流程不意味着每次强制创建 8–15 个页面。

## ingest 的执行阶段

### 1. 读取规则和冻结来源

优先采用用户指令及本地 Vault/Wiki 规则，通用技能补充未定义事项。规则文件和启用能力均记录内容摘要，进入预览依赖，防止审核期间规则变化。

保留已完整读取会话的不可变本地快照；为经验项保存 turnId、itemId、字段及范围。仅有模型概括或一个 evidence 字符串不足以支持来源归档。

第一版建议归档“已确认经验的原文证据包”：包括原始摘录、必要的前后修正、定位和完整会话快照 hash，明确标记为节选。人工意见单独记录，不能改写为会话原文；模型总结不能冒充原文。归档范围在预览中可见。未确认经验不进入知识正文。

正式来源路径采用 `40-LLM-Wiki/raw/codex/<sessionId>-<evidenceHash>.md`，最终批准前只在 ai-todos 草稿区保存。已发布原文不可覆盖；来源发生变化时生成新版本。

### 2. 检查 ingest 历史和检索已有知识

新增程序管理的 `raw/.manifest.json`，沿用 ingest 的来源 hash、导入时间及新建/更新页面清单，并记录本次审核版本。此路径适配本地 `raw/`，不另建 `.raw/`。manifest 的生成和写入也属于审核批次。

同一来源与相同审核内容已成功导入时，展示已有结果；失败任务不得写成已导入。会话新增内容或审核意见变化，视为新的输入，重新检查已知知识。

读取 index、hot，结合标题、别名、正文命中和已选页面的关联链接检索。分批读取相关页，避免把整库塞进一次模型请求。不能把“仅检查若干相关页”描述成全库无冲突；显示实际检索范围，预算不足时提示覆盖不完整。

### 3. 融合知识与处理冲突

优先更新既有知识页。新主题才新建概念、实体或对比页；不为每个提到的名词机械创建页面。已有页面补充新证据、范围和来源，保留原有有效内容。

会话来源记录使用本地 `wiki/chats/code/`，内容包括问题、调查、关键发现、解决方案、关联知识及未验证事项。外部材料有独立来源摘要价值时，再使用 `wiki/sources/`，不机械复制相同正文。

每项关系附证据：完全重复、补充、适用范围不同或直接矛盾。直接矛盾必须由用户选择保留旧结论、采用有依据的新结论，或并存待核实；并存时在双方添加对应 contradiction callout。选择后重新生成相关 diff 并重新检查，禁止静默覆盖。

### 4. 完成配套更新

- 新主题生成 Wiki 版与分类人读版；已有主题先检查并更新对应人读版，避免重复。
- 来源记录与知识页互链，相关旧页面按需补链；链接必须能解析到现有页或同批新页。
- 索引按现有类别更新。领域索引或 overview 存在且确有影响时更新，否则说明不适用，不新建空壳目录。
- 更新 `wiki/hot.md` 的近期变化和高价值上下文，保留仍相关内容并控制长度。
- 日志只新增本次记录，不改历史；沿用当前写入器的末尾追加语义，不重排已有混合顺序。
- 客服笔记继续更新对应 `_INDEX.md`，遵循按业务场景分类的本地约束。

### 5. 预检与完整预览

在“现有库 + 拟修改内容”上检查 frontmatter、中文标题、目录路由、引用、来源链路、重复路径、索引可达性、日志历史保留和 raw 不可变性。只要求本次变更不引入问题，不顺手修复全库历史问题。

检查结果以页面和经验项为单位可定位。结构错误阻塞批准；事实冲突须有明确处理决定；覆盖限制和未验证事项明确展示。用户编辑后重跑受影响检查，旧预览票据失效。

## 写入与兼容

预览包含所有拟写文件及其精确内容摘要，最终票据绑定候选版本、原文材料、规则和检索依赖。批准前重新校验；批准后仅写入该批内容，不再请求模型。

扩展现有受控写入器：Wiki Markdown、人读版 Markdown、raw 不可变来源、程序管理的 manifest JSON，各自有明确根目录及内容校验，不开放任意 Vault 路径。

沿用 journal 和失败恢复机制，不把多文件文件系统写入宣称为天然原子事务。接入现有 `wiki-lock.sh` 协议，在实际写入前按统一顺序获取相关锁、持锁重新检查基线、短时间完成写入后释放；锁无法取得时不写入。人读版位于外层 Vault，锁根目录必须区分并明确记录。其他编辑器未遵守 advisory locks 时，仍须依靠基线检查和保守恢复保护内容。

transport/mode 配置在正式执行前只读探测；尚无配置时向审核者显示采用的本地 filesystem 和目录规则，不提前运行会修改 Vault 的自动探测脚本。以后若启用其他 transport，必须满足精确内容、基线校验和恢复契约才可使用。当前未启用地址分配，不生成 address 或修改计数器。

旧候选保留历史记录；未经过完整 ingest 的待审核候选需重新生成方案，再开放最终批准。已经写入的记录不自动重跑，也不冒充已执行完整 ingest。

## 代码接入范围

- `src/codex.ts`：复用完整会话读取和分段模型接口，补充证据快照、逐阶段规划与可取消任务。

- `src/server.ts` / MCP bridge：提供生成方案、进度、冲突决策、校验和预览操作；最终批准仍只有本地浏览器可调用。

## 验收标准

在隔离 Vault 浏览器端到端覆盖：新增主题、补充已有主题、完全重复跳过、冲突三种处理、人工意见修改、规则/源/页面变化使方案失效、长任务恢复、锁竞争、多文件失败恢复。核对实际 raw、会话来源、知识页、人读版、索引、hot、日志和 manifest，而非只检查成功提示。正式 Wiki 继续不用于测试写入。
