# 经验沉淀改用原生 Codex Agent：调查与接入建议

日期：2026-11-16。状态：执行器已按方案替换；实施与验证见 [原生执行器说明](../wiki-native-agent.md)。下文保留替换前的调查依据与设计边界。

本次仅调查已有记录，没有重跑或修改该用户任务，也没有写入正式 Wiki。

## 替换前架构的职责问题

虽然用了 Codex，当前实现主要将它当作结构化模型调用接口：每段新建临时线程，禁用工具、MCP 和其他能力，由 ai-todos 自己读取完整源、分段、合并、筛选和回查。`withCodex` 还会拒绝服务端发来的工具或批准请求。

因此，用户提出的“让一个 Codex 会话执行知识整理任务”与现在的实现确实不同。接入需要改执行器和权限，不只是换一条提示词或拉长限时。

## 建议的职责划分

**Codex 负责整理知识。ai-todos 负责任务、审核和应用结果。**

1. 用户在 ai-todos 选择源会话、模型和强度后启动。
2. ai-todos 导出可信的不可变来源快照及索引到私有任务目录，保留 turn/item 定位；不先写入正式 raw 或 Wiki。
3. 每个经验任务使用一个独立后台 Codex 线程，不在原开发聊天追加分析指令。线程可只读检索指定源资料和 Wiki，按需读取，使用原生工具循环及上下文管理。
4. Codex 返回结构化候选，ai-todos 保存并展示；用户逐项确认、排除和补充意见。
5. 确认后执行完整 ingest 规划，输出全部拟变更、来源和冲突处理建议，仍只读正式 Wiki。
6. 最终批准由现有受保护写入器执行，检查候选版本、页面基线和已审内容；批准后不再让 Agent 生成新修改。

第一版可保持 Agent 全程 read-only：候选和拟修改正文通过最终 JSON 返回，草稿由 ai-todos 持久化。无需先给 Agent 草稿或正式 Wiki 写权限。

## 可以复用的原生能力

[官方 App Server 文档](https://developers.openai.com/codex/app-server/) 已说明：

- `thread/start` / `thread/resume`：建立和恢复线程。
- `turn/start` / `turn/steer` / `turn/interrupt`：启动、补充和取消当前轮次。
- `item/*`、`turn/*` 通知：流式内容、工具活动和完成状态。
- `thread/compact/start`：触发原生历史压缩，通过通知观察进度。
- 每轮可设置模型、推理强度、沙箱及 `outputSchema`。
- 沙箱可限制只读根目录；`thread/shellCommand` 明确不继承线程沙箱，不应用于本方案的 Agent 资料读取。

这些是官方协议能力，并不表示已在本插件试通所有功能。实施前须用当前安装的 Codex 验证工具调用、只读约束、恢复和压缩行为。

## 仍需由产品实现的部分

- 固定模型和推理强度；持久化 jobId 与 threadId，保存阶段、最近活动、耗时、错误和最终产物。
- 不把 Stop、沉默或原生压缩完成当作任务完成；以明确轮次结果和结构化输出校验为准。
- 完整性与出处检查仍属于产品契约；原生压缩不保证永远保留所有关键证据，来源快照应可重读。
- 后台线程和来源线程分别标记，防止分析自己的分析任务或污染正常会话列表。
- 输入资料是不可信数据。只允许读取本任务所需的资料，限制工具与网络；不能把通用执行器的权限一并放开。
- 用活动进度、可取消操作和任务总预算管理长任务；不再以统一 120 秒整轮限时冒充“卡死检测”。原生会话仍可能遇到网络、模型或服务端超时。

## 与既有方案的关系

保留模型选择、逐项人审、Markdown、候选历史、Wiki diff 和最终批准写入器。替换当前自制的 chunk/merge/curate 编排执行层；完整 ingest 的本地规范和人工批准边界不变。

建议先对“总结免佣卡下单支付问题”和 STE 会话做隔离原型，核对有效知识、出处、原生工具读取、取消/恢复和正式 Wiki 零写入。原型通过后再替换正式入口，保留旧结果作为对照；当前不宣称该方案已经落地。
