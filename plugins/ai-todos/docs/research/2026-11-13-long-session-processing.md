# Agent 长会话经验提取：资料与方案

调研日期：2026-11-13。范围是 ai-todos 的手动会话经验提取，不涉及自动写入正式 Wiki。下面的第一手资料说明通用技术，并不证明某种算法在本项目中的召回率或耗时。

## 当前实现与瓶颈

- `src/wiki-thread-reader.ts` 以 `thread/items/list` 顺序分页，按完整 `page.data` JSON 的 UTF-8 字节累加；超过 800,000 字节直接报错，并非模型报告的上下文上限。它还会读取两遍比对快照，确保会话读取期间未变化。
- `src/codex.ts` 当前将整份会话条目一次送入独立的 `assess` 模型轮次。连接层有单帧或缓冲约 2,000,000 的独立上限；会话读取和模型轮次分别有 30 秒、240 秒限制。放宽 800 KB 只能移走其中一个限制，不能保证请求完成。
- 尚未获得截图对应的会话 ID 与实际体积分布；不能断言究竟是工具输出、消息或其他字段占大头。字节数也不是 token 数。模型、语言、工具包装及输出预算均影响可用上下文。
- 本地 [[agentic-large-data-analysis]] 记录过某次大输入异常及“分层整理、按需下钻、结论附证据”的经验。该案例依赖当时的代理和请求协议，不能推广为所有 Responses 请求的普遍根因。

## 一手资料和可迁移结论

1. [OpenAI Cookbook：Summarizing Long Documents](https://developers.openai.com/cookbook/examples/summarizing_long_documents) 演示按 token 与分隔符切段，逐段生成摘要；增加段数可提高输出细节，但示例的调用次数和耗时也随之上升。递归模式携带之前摘要，可能改善连贯性，但计算成本更高。
   - **不能照搬示例**：示例对单个超过预算的段执行 `continue` 并仅打印警告；递归模式还把所有之前摘要拼进每轮上下文，长期会增长。对需要可追溯经验的本项目，这会导致不可接受的遗漏或再次超限。
2. [Anthropic：Effective context engineering for AI agents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) 讨论上下文压缩、结构化记录与按需检索，明确指出过度压缩会丢失之后才显出重要性的细节，并建议先在复杂轨迹上重视召回，再优化精度。其描述是厂商实践建议，不是本项目的效果数据。
3. [LangChain：RAG with Deep Agents](https://docs.langchain.com/oss/python/deepagents/rag) 描述切分、检索、把较大文档卸载到文件系统并按需访问的模式。该文档的 `chunk_size=1000, chunk_overlap=200` 是示例设置，不能当作此场景的最佳值。对经验发现任务，仅靠检索已知关键词可能漏掉事先不知道的教训。
4. [OpenAI：Compaction](https://developers.openai.com/api/docs/guides/compaction) 说明压缩输出是供后续模型调用使用的不透明条目，并非面向人类阅读的原始证据；调用该能力也有模型、接口与上下文大小前提。不能把不透明状态当成可核验的 Wiki 依据，也不能假定当前 Codex app-server 已暴露该能力。
5. [Liu 等：Lost in the Middle（TACL 2024）](https://aclanthology.org/2024.tacl-1.9/) 在所测的多文档问答、键值检索和当时模型中观察到位置敏感。它支持为长输入设置位置和跨段评估，不直接证明当前所用模型或本项目经验提取一定有相同幅度的退化。

## 面向 ai-todos 的建议设计

**建议从分块提取、分层合并、回读证据起步；不要把整份原文一次送给模型，也不要只依赖一次全局摘要。**

1. **枚举与快照**：以 session/turn/item 标识按顺序枚举，记录快照边界、总条目、每页/条目的大小和类型。采用稳定快照或源哈希检查，避免分析期间会话变化；这一环仍要实测 Codex API 分页上限、单页及单条超长行为，不能假设光把 page limit 调小就解决单条超大响应。
2. **可审计分段**：优先保持 turn 及工具调用与结果配对；预算基于实际可用 token 估计并同时限制序列化字节，保留提示词、结构化输出和模型回答余量。相邻段按需要保留少量重叠；可配置且通过实际样本评估。
3. **单条过大**：递归分段大文本，记录相同 turn/item ID 与片段起止位置；二进制和多模态内容显式标记已跳过或不可分析，不静默截断。若宿主 API 单条响应即超过传输限制，需验证其他可靠的只读读取方式；不可凭空承诺一定能读取。
4. **逐段产出经验候选**：结构化列出事实、证据、适用条件、未验证项、后续修正或冲突；保留来源 turn/item/片段范围，不把不成功、未覆盖与“没有经验”等同。
5. **分层归并和证据回读**：对每段候选限大小分层去重、合并，按原始顺序关联前因后果和后续纠正；跨段冲突的结论需回读原片段核验，重复片段按原始证据 ID 去重。摘要是索引，证据应可回看原文；不可因为合并次数多就将事实视为已证实。
6. **人工确认后才对照 Wiki**：先展示会话做了什么和逐项候选，允许确认、排除及补充意见；仅对已确认项运行 Wiki 检索/冲突判断；正式写入继续绑定用户预览、目标文件快照与最终人审。
7. **后台任务与可恢复进度**：页面展示阶段、分段完成数、错误段和可重试状态；每段结果与覆盖清单本地持久化，限制并发和总预算，提供取消和超时，不靠一条 HTTP 请求等待整个分析。中断/重试要用会话快照哈希 + 分段 ID + 提取版本作幂等键，并在重新运行前检查源会话变化；清楚提示输入数据发送到何种模型。失败段不得显示“全部分析完成”。
8. **最小数据与隐私**：模型只收到处理该段所需内容；不要默认向外存储全部原文。保留原始证据的回读能力需遵循用户既有会话存储权限与生命周期，日志不得打印会话或密钥。脱敏、保留时间和可删除性须明确设计。

## 验证计划与边界

- 先只读测量用户实际报错会话：总字节、条目数、类型/单条大小分布及转义后请求大小；不打印正文，也不假设原因是工具输出。
- 设计标注样例：短/长、单条超长、跨段根因及修正、重复、无经验、缺失/多模态条目、读取中追加、分页循环、超时重启、速率限制。检查每段覆盖及证据 ID 可定位，测经验召回/错误合并/事实支持率、总耗时、峰值、失败率、token 与费用；人工审核准确性，避免仅测“接口返回成功”。
- 在真实用户会话上比较单次短输入基线及分段结果；不得在实验中自动批准或修改正式 Wiki。现阶段仅为调研方案，阈值、效果和兼容性均未实测。
